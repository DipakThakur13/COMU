**Model correction.** This run was launched naming `nvidia/nemotron-3-ultra-550b-a55b`. That label was wrong. The runtime's defaultProviderFactory does not pass the requested modelId to the NVIDIA provider, which falls back to its built-in default, so every model request in this run was served by Nemotron 3.5 Lightning 30B-A3B, as the model field of each model_request.succeeded event shows. The records were written with the name the run was launched under; this report names the model that served them. The defect is recorded in docs/B0_FINDINGS.md.

**Limitations.**

- Repair caveat: the repair budget (maxRepairTimeMs, 180 s) is measured from the start of the task, not the start of repair. Any verification failure more than three minutes into a task ends with REPAIR_TIMEOUT before a single repair attempt, so a failure class of REPAIR_TIMEOUT with 0 repair attempts reflects this defect, not repair exhausted.
- T7 zeros are an instrument result, not a capability result. The read-only onboarding tasks are verified anyway, because verification requiredness is derived from prompt wording rather than from the task contract; both T7 TypeScript fixtures fail their own typecheck in their untouched state; and the rubric then scores whatever text the failed run left. Peak context in T7 stayed at 1.7-5.2% of the window. See docs/B0_FINDINGS.md.
- The typecheck signal carries no information for T1-T4. Those fixtures declare their typecheck as node --check, which in Node 22.14 exits 0 on any file containing an export without checking it. A passing typecheck there says nothing about the code. Correctness is unaffected: the grader runs the tests, not the typecheck.
- This is rep 1 only, one run per fixture. B0 was planned at five repetitions and stopped after rep 1 when the NVIDIA gateway began refusing most requests; reps 2-5 were abandoned and are not reported here. At n=1 a single fixture's result cannot separate signal from noise. The one false completion B0 recorded (t2-py-validator rep 2) is in an abandoned repetition, so the zero below is a rep 1 count, not evidence that false completions do not occur. It is analysed in docs/B0_FINDINGS.md.
- t3-ts-extract was ended by the harness's own 30-minute wall clock, not by COMU or the provider, after 7 slow model requests with the refactor incomplete. The harness limit is shorter than the budget it allows (25 minutes of execution plus up to 10 minutes for a request already in flight), so a slow provider can end a cell at the harness. It stands as a failure: the grader found the refactor incomplete.

## Reading a delta against this run

A change smaller than the run to run spread is no detected change. Specifically:

- A fixture moving by one repetition out of 1 is noise, not a result.
- A fixture moving by two or more is a signal for that fixture.
- A suite level claim needs two or more fixtures moving by two or more in the same direction.
- A continuous metric has moved only when the two runs' ranges do not overlap.
- A failure class has moved only when its count changes by more than the number of fixtures that moved.
